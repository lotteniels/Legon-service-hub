# B-Tree Evidence — Tree Structures Pod

**Structure:** `com.campushub.structures.tree.BTree`
**Used by:** M6 Indexing Engine (indexing service requests / locations by key)
**Configuration for this walkthrough:** minimum degree `t = 2`, so each node holds at most
`2t - 1 = 3` keys and at least `t - 1 = 1` key, and has at most `2t = 4` children.

`t = 2` is used here only because it makes the tree small enough to draw by hand. The
production default in the code is `t = 3` (max 5 keys per node).

## 0. The tree used in both sections below

Keys inserted in this order: **10, 20, 5, 6, 12, 30, 7, 17**

Resulting tree (printed directly by `BTree.structureAsText()`):

```
B-Tree (t=2, max 3 keys/node, size=8, height=1)
[10 | 20]
  [5 | 6 | 7]
  [12 | 17]
  [30]
```

Read that as:

```
                    +----------+
                    | 10 |  20 |          <- root, 2 keys, so 3 children
                    +----------+
                   /     |      \
                  /      |       \
        +------------+  +-------+  +------+
        | 5 | 6 | 7  |  | 12|17 |  |  30  |
        +------------+  +-------+  +------+
         keys < 10      10<k<20     k > 20
```

In-order traversal returns `[5, 6, 7, 10, 12, 17, 20, 30]` — sorted, which confirms every
key ended up in a subtree consistent with the keys above it.

## 1. Step-by-step: how the code searches for an item

The rule inside a node is: *walk left to right until you meet a key that is not smaller
than the one you want.* If it is equal, stop — found. If it is bigger, drop into the child
sitting immediately to the left of it, because that child holds exactly the keys that fall
between the key before it and the key after it. Repeat until found, or until you run out of
tree at a leaf.

### 1a. Searching for a key that IS present: `search(17)`

| Step | Where we are | What we compare | Decision |
|------|--------------|-----------------|----------|
| 1 | Root `[10 \| 20]`, slot 0 | 17 > 10 | Too small, move right inside this node |
| 2 | Root `[10 \| 20]`, slot 1 | 17 < 20 | Stop here; 17 must live between 10 and 20 |
| 3 | Follow child 1 | — | Descend one level |
| 4 | Leaf `[12 \| 17]`, slot 0 | 17 > 12 | Move right inside this node |
| 5 | Leaf `[12 \| 17]`, slot 1 | 17 == 17 | **FOUND** at slot 1 |

**Result: found after visiting 2 nodes and 4 comparisons.**

Raw output from `BTree.searchWithTrace(17)` (this is generated by the code, not written by
hand — rerun `BTreeManualTest` to reproduce it):

```
Level 0: arrive at node [10 | 20]
  compare 17 > 10  -> keep moving right
  compare 17 < 20  -> stop at slot 1
  follow child 1 (holds keys between the neighbours above)
Level 1: arrive at node [12 | 17]
  compare 17 > 12  -> keep moving right
  compare 17 == 17  -> FOUND at slot 1
FOUND after visiting 2 node(s) and 4 comparison(s)
```

### 1b. Searching for a key that is NOT present: `search(8)`

```
Level 0: arrive at node [10 | 20]
  compare 8 < 10  -> stop at slot 0
  follow child 0 (holds keys between the neighbours above)
Level 1: arrive at node [5 | 6 | 7]
  compare 8 > 5  -> keep moving right
  compare 8 > 6  -> keep moving right
  compare 8 > 7  -> keep moving right
  this node is a leaf, so there is no child to follow -> NOT FOUND
NOT FOUND after visiting 2 node(s) and 4 comparison(s)
```

The important detail: the failed search costs the same *number of node visits* as the
successful one. A B-Tree search always walks from the root to a leaf at worst, so the cost
is set by the height of the tree, not by luck.

### 1c. Why this is cheap

- Number of nodes visited is at most `height + 1`.
- Height is about `log_t(n)`, so with `t = 3` and 10,000 keys the height is 8 in the worst
  case measured by the test suite, and typically far less.
- Within one node we do at most `2t - 1` comparisons, which is a small constant.
- Overall: **O(log n)** comparisons, and — the reason databases use this structure — only
  `O(log_t n)` *node* reads, where each node is one disk page holding many keys.

## 2. How and why a node splits when it gets too full

### 2a. The rule

A node is **full** when it holds `2t - 1` keys (3 keys when `t = 2`). We never let a node
hold more than that. Before inserting into any node on the way down, if a child we are
about to enter is full, we split it *first*. This is called a pre-emptive or proactive
split, and it means a split never has to cascade back up the tree.

Splitting one full node with `2t - 1` keys produces:

- a **left** node with the smallest `t - 1` keys,
- a **right** node with the largest `t - 1` keys,
- and the single **median** key, which is pushed **up** into the parent, where it sits
  between the pointers to those two nodes.

Count check: `(t-1) + (t-1) + 1 = 2t - 1`. No key is lost or duplicated; the over-full box
simply becomes two comfortable boxes plus one key promoted.

### 2b. Worked example — the split that happened above

After inserting 10, 20, 5 the whole tree is one node, and it is now full:

```
[5 | 10 | 20]       <- 3 keys = 2t-1, full
```

Now insert **6**. The root is full, so it must split before anything else happens. The
median key is the middle one, **10** (index `t - 1 = 1`):

```
Step 1: median 10 is chosen
        [5 | 10 | 20]
              ^ median

Step 2: split into two halves
        left: [5]        right: [20]

Step 3: 10 moves UP into a brand-new root
        [10]
        /   \
      [5]   [20]

Step 4: NOW insert 6. At the root, 6 < 10, so go left. [5] is not full, so 6 goes in.
        [10]
        /   \
     [5|6]  [20]
```

Then 12 and 30 go into the right leaf, giving `[12 | 20 | 30]`, and 7 goes into the left
leaf, giving `[5 | 6 | 7]`. Finally inserting **17** hits the second split: the child
`[12 | 20 | 30]` is full, so it splits with median **20** moving up beside 10, and 17 then
lands in `[12]`, producing the final tree in section 0.

### 2c. Why splitting upwards is the whole point

- **The tree can only grow at the root.** Splitting pushes a key *up*, never down, so the
  only way the tree gets taller is when the root itself splits. When that happens every
  leaf gets one level deeper at the same moment.
- **Therefore every leaf is always at the same depth.** This is the B-Tree's balance
  guarantee, and it is structural: there is no rebalancing step, no rotations, no colour
  flipping. It is impossible for the tree to become lopsided.
- **Compare with a plain BST.** Insert 1, 2, 3, ..., 10,000 into a BST and you get a
  10,000-node chain, and search degrades to O(n). The test
  `sortedInputStaysBalanced` inserts exactly that sequence into this B-Tree and asserts the
  height stays at or under 8.
- **Cost of the split itself** is O(t): copying `t - 1` keys into a new node and shifting
  the parent's arrays by one. Splits are also rare — a node only splits after `t` more
  insertions land in it.

### 2d. The mirror image, for completeness

Deleting has the opposite problem: a node can drop *below* `t - 1` keys. The code handles
it symmetrically — on the way down, if the child we are about to enter has fewer than `t`
keys, it either **borrows** a key from a sibling that has a spare one, or **merges** with a
sibling and pulls the separating key down from the parent. If a merge empties the root, the
root is replaced by its only child and the tree gets one level shorter. Growth and shrinkage
both happen at the root, which is why the equal-depth property survives both.

## 2e. Team-derived parameter (brief section 2)

The minimum degree `t` is not a number we picked. It is computed from the team's index
numbers by `BTree.minDegreeFromIndexNumbers()`:

```
t = 2 + (sum of member index numbers mod 4)      giving t in 2..5
```

So the node capacity, the tree's height at every input size, and every trace table in this
report are specific to this team. Change the team and the tree changes shape.

**Be able to compute this by hand at the defence,** and to answer the follow-up: a larger `t`
means more keys per node, therefore a *shorter* tree (fewer node visits) but *more*
comparisons inside each node. That trade-off is the whole design question behind B-Trees.

Two further parameters in the performance experiment are derived from the same index
numbers: the random seed that fixes key order, and the offset used to construct
guaranteed-miss lookups.

## 2f. Proof sketch and loop invariant (brief section 10)

### Loop invariant for the search loop

The inner loop of `get`:

```java
int i = 0;
while (i < x.n && compare(searchKey, x, i) > 0) {
    i++;
}
```

**Invariant:** at the top of every iteration, every key in `x.keys[0 .. i-1]` is strictly
less than `searchKey`.

- **Initialisation.** `i = 0`, so the range `keys[0 .. -1]` is empty and the claim holds
  trivially.
- **Maintenance.** The loop only advances `i` when `searchKey > keys[i]`. So `keys[i]` joins
  the range only once it is known to be smaller than the target, and the invariant still
  holds for `i+1`.
- **Termination.** The loop ends when `i == x.n` or `searchKey <= keys[i]`. Combined with the
  invariant, at that point every key before `i` is smaller than the target and (if `i < n`)
  `keys[i]` is greater than or equal to it. Therefore either `keys[i]` equals the target, or
  the target lies strictly between `keys[i-1]` and `keys[i]` — and by the B-Tree ordering
  property, the only place it can be is `children[i]`. Descending into `children[i]` is thus
  the correct move, which is exactly what the code does.

`i` increases by one each iteration and is bounded by `x.n`, so the loop always terminates.

### Correctness of insertion, by induction on height

**Claim:** after any sequence of `put` calls, the structure is still a valid B-Tree — all
leaves at equal depth, every non-root node holding between `t-1` and `2t-1` keys, and keys
ordered consistently with the subtree bounds.

- **Base case.** A new tree is a single empty leaf root. Valid by definition (the root is
  exempt from the minimum-keys rule).
- **Inductive step.** Assume the tree is valid before an insertion. `insertNonFull` is only
  ever called on a node that is not full, because the caller splits a full child *before*
  descending, and splits the root before starting. So there is always room for a promoted
  median key, and a split never needs to propagate upward — one split resolves one overflow.
  `splitChild` moves `t-1` keys right, keeps `t-1` left, and promotes exactly one: total
  preserved at `2t-1`, and both halves satisfy the minimum. Keys move only within the range
  their subtree already covered, so ordering is preserved. Depth changes only when the root
  itself splits, and that adds one level beneath *every* leaf simultaneously, so equal depth
  is preserved. Hence the tree is valid after the insertion.

**This is checked mechanically, not just argued.** `BTree.validate()` re-verifies all of
these properties, and the test suite calls it after every operation across thousands of
randomised inserts and deletes. A proof sketch plus an executable invariant check is stronger
evidence than either alone.

## 3. How these claims were verified

`BTreeTest` / `BTreeManualTest` assert all of the following:

| Check | How |
|-------|-----|
| Required cases (normal add/find, empty tree, single item, duplicate) | Four dedicated tests |
| A node splits at exactly the 4th key when `t = 2`, and height increases by 1 | `nodeSplitsWhenFull` |
| Sorted input does not unbalance the tree | `sortedInputStaysBalanced`, 10,000 ascending keys |
| Every structural rule holds after every operation | `BTree.validate()` re-checks key counts, key ordering, subtree bounds, and that all leaves sit at one depth |
| Insert, delete and lookup are correct in general | 5,000 random operations per `t` value compared key-for-key against `java.util.TreeMap` |

`validate()` is the strongest piece of evidence here, because it does not test outputs, it
tests the invariants — the tree is asked to prove it is still a legal B-Tree after every
single split and merge.
